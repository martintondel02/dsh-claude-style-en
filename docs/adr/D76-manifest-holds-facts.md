# D76. The manifest records the facts the interface and the build need

- **Replaces**: D42, D13, D29, D39, D72

## Background

A feature writes all of its facts into a manifest, and the settings page's rows are collected from manifests too, so the problem of scattered registration converged. The manifest also carried a description in Chinese and English, which was an introduction for readers: its only reader was an "Overview of features" generated from the manifests, that document was opened by nobody, the two paragraphs only grew, and changing one feature meant rewriting them in two languages. What the page and the build read was never those descriptions; a reader learns about this plugin from the README's screenshots and the settings page itself.

## Decision

- Each feature writes all of its facts into one manifest: install order, whether it is deferred, the host contracts it depends on, the other feature handles it reads, its stylesheet and its position in the whole stylesheet, its settings rows, the checks that cover it, and its yielding to the upstream. Adding a feature adds one directory.
- The manifest records only the facts the interface and the build need; text written for readers does not enter the manifest, and no document is generated from the manifest.
- Each feature declares exactly one of the two: which preference key it hangs on, or a sentence saying why it has no switch. Both, neither, or a declared key that is not in the preference table is rejected by type checking and by the build.
- The meaning of a switch is "off equals the host as it was": turning it off runs the feature's own teardown, turning it on installs it again, and the page never reloads. Several features may share one switch or different values of the same choice.
- Only features whose absence the first screen can bear are deferred. A feature that rewrites host interface on the first screen stays in the main artifact. A deferred feature's modules form a chunk of their own, requested after the page has been taken over; a feature that reads it before the chunk arrives treats it as absent, and a chunk that arrives after this generation has ended is not installed.
- The dependencies between features are enforced by type checking: a feature module sees only the handles it declares, and a read it has not declared is rejected at type check time.
- Settings rows are registered by ownership: a feature registers each of its settings rows in its own manifest, each row binding one preference key and stating the control kind (switch, segmented, preview card, custom), the tab it sits on, its rank, its copy key, and the other rows it depends on (`requires`, `windowsOnly`, follows the row above).
- Values are read from the preference table (D73): segmented controls and preview cards no longer each write a value set; the manifest writes only the copy key of each value.
- A control with a preview or a custom form is a `<feature>.settings.ts` in the feature's directory: the control is code, and it lives beside the feature it serves; the build collects these modules by feature into the settings page chunk.
- Interface copy is a `<feature>.copy.json` in the feature's directory: one Chinese and one English string per key. The build compiles it into the feature's module — the main artifact for a feature in it, the feature's own chunk for a deferred one.
- Code writes keys only: call sites write the key alone, and no English fallback is written at the call site any more; the key's type is generated by the build from that feature's copy file, and a misspelled key is rejected at type check time.
- Model copy remains a data document (D5): `model-descriptions.json` keeps only the rules for model families, tiers and vendors.
- The manifest is still data: the build evaluates manifests in Node, component modules and copy are evaluated only in the browser, the manifest refers to their module names, and the build checks the files exist.
- The build collects install order, stylesheet concatenation order, the settings page's rows, check scope and the yielding to the upstream from the manifests, so no place writes a second copy; and it rejects an unregistered settings row, one preference bound by two rows, a control module that does not exist, a copy key absent from its feature's copy file, and a copy pair missing one language.

## Consequences

- Adding a settings row changes only the feature's own directory; the settings page does not grow with the number of features.
- The settings page's rendering converges into one page assembled by tab and rank, its appearance decided by the manifest and the control modules; a visual change is checked by hand in both light and dark.
- Once interface copy travels in the feature's artifact, the first screen need not wait for the copy document: interface copy is there on the first screen, and when the model copy arrives only the model picker repaints.
- The manifest's shape has to stay stable; stylesheet order is written as a rank, and inserting a new stylesheet means picking an empty slot.
- A deferred feature arrives one request later than the main artifact, and the related interface does nothing until it does; the module ownership of the main artifact and the chunks has to be worked out over and over until no module is carried by both.
- Turning a feature off requires its teardown to hand the host interface back completely in mid-run, at the cost that every feature needs its checks written for both the switch on and the switch off.
- When two features use one copy file, either each writes its own or it is registered in the settings feature and referenced by name from both places.
- The repository has no per-feature documentation: what a feature does is read from the README's screenshots, the row on the settings page and the changelog.
- Abandoned: keeping the descriptions in the manifests for a document or the README to reference (each feature would still need its description in two languages, and changes would land only in text the reader never sees).

## Reconsider when

- When the loader provides asynchronous chunking or asset addresses inside a plugin, deferred modules use the loader's mechanism.
- When the host provides a way to read plugin copy, or a translation service for interface copy, interface copy connects to the host's.
- When the host provides a unified form for rendering the settings page, the settings rows in the manifest are handed to the host's structure.
